# OpenAI spend uses BudgetGuard and job caps

SnapSync pays the model bill. One intentional act must not become dozens of OpenAI calls: an operator issue-triage script can loop, and seller Bulk SEO / ungrouped upload already fan out one call per product or photo. We therefore use **two controls**, not one meter.

**Issue-triage script** (`scripts/issue-triage/`): every OpenAI call goes through **BudgetGuard** in `budget.py`. Model from `OPENAI_MODEL` (default `gpt-6-luna`); never pass `Astra` as `model=`. Hard `max_steps` of 10 model turns; refuse the next call if the run would exceed 50k tokens total or 10 calls. Fail closed (non-zero exit); no retry-to-finish. Keep the last three tool results; older ones become one-line summaries. Trim GitHub payloads to title, labels, URL, and the first 500 characters of body. Put fixed system instructions and tool schemas first, changing data last. v1 is read-only GitHub (issue + labels) and draft-only output; live API only after an explicit ask in chat; tests use a mock that asserts call count, prompt shape, and ceiling refusal. This path is not wrapped into `api-py`’s `get_openai()`, and it is not a seller Destination.

**Product path** (`api-py`, today’s `gpt-5.2`): not wrapped in BudgetGuard. Hard job caps instead: at most **20** ungrouped vision analyzes per upload act, and at most **25** eligible primary products per Bulk SEO Start — refuse the act above those limits, do not silently process a prefix. Langfuse stays operator observability (ADR 0024). Seller billing stays **listing-copy write** (ADR 0040); these caps do not change that meter.

**Considered:** one BudgetGuard around all `get_openai()` calls (conflates agent loops with seller jobs); unlimited Bulk SEO with overage as the only backstop (ADR 0016 — amended here for OpenAI fan-out, not for listing-copy write price); soft continue after max steps (how a “one request” run climbs toward dozens of calls); `--live` / `--apply` in v1 (deferred until draft-only is proven).
