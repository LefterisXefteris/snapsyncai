# Production API waits for CI; thin post-deploy smoke

Production FastAPI on Railway keeps auto-deploy from `main`, but the service enables Railway **Wait for CI** so a commit only deploys after that commit’s GitHub Actions workflows succeed. Merge to `main` requires a PR and the four CI jobs (`web`, `api`, `secrets`, `deps-security`), with admin bypass allowed as in ADR 0044. After a successful Railway production deploy, a separate Actions workflow curls `https://api.snapsyncai.co.uk/api/health` and asserts `status`/`service`; that workflow must not run on `push` to `main` (Wait for CI waits for every workflow on the commit and would deadlock). Smoke failures surface as a failed Actions run only — no auto-rollback. Staging, authenticated live-path smoke in CI, and auto-rollback stay out of this cut; `/live-path` remains the human/agent ship discipline for seller-visible paths.

**Considered:** a `staging` Railway environment before prod (deferred until auto-deploy + thin smoke are boring); GitHub `railway up` instead of Wait for CI (moves deploy ownership off Railway); authenticated live-path smoke against prod (needs a durable test seller and secrets); auto-rollback when smoke fails (too sharp while the check is only health); putting smoke on `push` to `main` (deadlocks Wait for CI).
